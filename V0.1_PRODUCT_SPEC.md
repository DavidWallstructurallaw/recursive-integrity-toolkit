## 1. Product statement

Recursive Integrity Toolkit v0.1 is a local-first, auditable research toolkit for examining recursive closure risk in synthetic-data and recursive-data pipelines.

The toolkit accepts records, optional provenance manifests, optional lineage data, and optional historical dataset versions. It reports the strongest conclusions supported by those inputs while preserving uncertainty where evidence is incomplete.

v0.1 focuses on five practical questions:

1. How much of the analyzed dataset can be traced to declared sources?
2. Does the available representation show support or diversity contraction?
3. Which low-frequency states appear vulnerable under a declared closed-resampling scenario?
4. Does a large dataset depend on a narrow set of external ancestors?
5. Which conclusions remain unavailable because provenance, lineage, representation, or outcome evidence is missing?

The product is designed as a reference implementation that researchers and maintainers can inspect from input schema through final report.

---

## 2. Product thesis

Recursive systems can appear large, fluent, or stable while their effective support, external ancestry, and correction channels narrow.

A useful audit tool should therefore measure visible structural conditions without pretending to observe hidden processes.

The product thesis has four parts:

### 2.1 Recursive closure must be evidence-bounded

Closure claims depend on declared provenance, external grounding, and lineage evidence.

Unknown origin remains unknown.

### 2.2 Diversity must be representation-bound

Support and diversity have meaning only under a declared state representation such as topic, label, bin, cluster, or exact record form.

### 2.3 Tail risk must remain assumption-bound

Rare-state extinction probabilities belong to an explicit finite closed-resampling scenario. They are not automatically calibrated forecasts of a real training pipeline.

### 2.4 Reports must separate knowledge from interpretation

Every result is classified as:

- observed fact,
- derived metric,
- proxy signal,
- simulation,
- unavailable conclusion.

## 4. Primary user problems

v0.1 addresses the following recurring problems.

### 4.1 Provenance exists but remains incomplete

A pipeline may contain some source labels while lacking complete row coverage, grounding status, generator identity, or parent links.

The toolkit must measure those gaps separately rather than presenting one inflated provenance score.

### 4.2 Record count exaggerates independent support

A dataset may contain many rows that descend from a small ancestor set.

The toolkit must report both apparent record count and effective ancestry breadth.

### 4.3 Tail loss hides behind average quality

Broad averages can remain stable while low-frequency topics, labels, or states disappear.

The toolkit must expose support loss and tail extinction under a declared representation.

### 4.4 Recursive scenarios are confused with production forecasts

A mathematically exact closed-resampling probability can be useful while still depending on assumptions that a real pipeline may not satisfy.

The toolkit must preserve that distinction.

### 4.5 High-level warnings cannot be audited

Users may receive a risk score without knowing how it was produced.

The toolkit must expose definitions, inputs, formulas, tests, and report fields.

## 5. Product principles

### 5.1 Auditability before feature breadth

A smaller transparent toolkit has higher priority than a larger opaque platform.

### 5.2 Explicit unknowns

Missing evidence widens uncertainty.

It does not authorize inference.

### 5.3 Local-first operation

The default workflow requires no cloud service, account, database server, telemetry, or remote model.

### 5.4 Deterministic behavior

The same inputs and configuration should produce the same outputs.

Simulation requires fixed or recorded seeds.

### 5.5 Sidecar metadata

Users should be able to add provenance without rewriting source records.

### 5.6 Traceable public outputs

Every public result must map to:

```text
definition
-> rule or mathematical object
-> implementation module
-> test
-> report field
-> documented limit
```

### 5.7 Capability-based honesty

A maximum observability level is supplemented by a capability matrix.

A higher level does not imply complete evidence for every analysis family.

## 8. Supported inputs

### 8.1 Required input

One records file.

Supported required formats:

- CSV
- JSONL

Parquet is recommended as an optional extra.

### 8.2 Optional inputs

A run may include:

- provenance manifest,
- schema mapping file,
- configuration file,
- one or more historical dataset versions,
- user-provided embedding file,
- explicit version-order file,
- external reference distribution for an approved scenario.

### 8.3 Minimum records schema

Required canonical fields:

| Field | Type | Product requirement |
|---|---|---|
| `record_id` | string | Unique within `dataset_version` |
| `content` | string or local reference | Primary analyzable payload |
| `dataset_version` | string | Stable version identifier |

### 8.4 Common optional record fields

| Field | Type | Intended use |
|---|---|---|
| `topic` | string | State representation |
| `label` | string | State representation |
| `timestamp` | datetime | Ordering and metadata |
| `embedding_ref` | string | User-provided representation |
| `weight` | float | Optional weighted analysis |
| `batch_id` | string | Grouping |
| `notes` | string | Private metadata, excluded from normal logs |

### 8.5 Provenance manifest

The provenance manifest may contain:

- source type,
- provenance confidence,
- external grounding,
- parent references,
- generator ID,
- generator version,
- transformation,
- generation,
- human review flag,
- batch ID,
- notes.

Exact field rules belong in `DATA_AND_PROVENANCE_SPEC.md`.

### 8.6 Parent references

The recommended canonical parent reference uses a composite key:

```text
dataset_version::record_id
```

Multiple parents are represented as a JSON array.

Example:

```text
["v1::v1_01","v1::v1_02"]
```

This behavior remains subject to approval of `UD-006`.

### 8.7 Local content references

When `content` is a local reference:

- local file resolution may be supported,
- remote retrieval is disabled by default,
- unresolved references block content-dependent analysis,
- metadata-only analysis may continue when limitations are reported.

## 11. Representation model

### 11.1 Product requirement

Support, diversity, tail, and extinction are always calculated under a declared representation.

### 11.2 Recommended selection order

Pending approval of `UD-011`:

1. explicit configuration,
2. `topic`,
3. `label`,
4. user-provided embedding bins or clusters,
5. exact normalized content hash.

### 11.3 Representation metadata

Every related result includes:

- representation name,
- representation source,
- representation version,
- mapping or binning rule,
- fallback status.

### 11.4 Exact record-form support

Exact normalized content hash may support:

- exact duplicate count,
- unique normalized record count,
- record-form support.

It must not be labeled semantic support.

### 11.5 Cross-version compatibility

Longitudinal analysis requires compatible representation definitions.

A representation change may produce:

- a blocked comparison,
- a partial capability status,
- a warning,
- separate per-version metrics without a direct delta.

## 12. Observability model

### 12.1 Maximum level

The toolkit reports one maximum observability level from 0 through 5.

### 12.2 Capability matrix

The toolkit also reports capability-specific status.

Allowed statuses:

- `available`
- `partial`
- `unavailable`
- `experimental`

Required initial capabilities:

- ingestion,
- content diagnostics,
- provenance,
- lineage,
- dataset longitudinal comparison,
- model longitudinal comparison,
- intervention simulation.

### 12.3 Level 0

Minimum evidence:

- readable input,
- minimal schema.

Allowed outputs:

- file inventory,
- row count,
- schema coverage,
- validation status,
- auditability gaps.

### 12.4 Level 1

Minimum evidence:

- analyzable content or declared representation.

Allowed outputs:

- exact duplicates,
- support size,
- Gini-Simpson diversity,
- rarity ranking,
- tail membership,
- approved finite-resampling scenarios.

### 12.5 Level 2

Minimum evidence:

- partial or complete provenance.

Allowed outputs:

- provenance row coverage,
- required-field coverage,
- grounding-field coverage,
- source-type shares,
- unknown share,
- direct closure exposure bounds.

### 12.6 Level 3

Minimum evidence:

- at least one resolvable parent-child path,
- cycle-free analyzed lineage subgraph.

Allowed outputs:

- lineage coverage,
- external-root tracing,
- shared ancestors,
- ancestry incidence,
- ancestry concentration,
- lineage closure exposure bounds.

### 12.7 Level 4

Minimum evidence:

- at least two ordered, representation-compatible dataset versions.

Allowed outputs:

- version deltas,
- support loss,
- tail extinction,
- provenance change,
- lineage change where available.

Model-performance trends require separate model evidence.

### 12.8 Level 5

v0.1 interpretation:

- optional,
- experimental,
- scenario-based.

Allowed outputs:

- explicit closed-resampling comparison,
- explicit external-reopening comparison,
- assumption table,
- fixed-seed simulation.

No empirical causal conclusion follows from Level 5 simulation alone.

## 13. Core diagnostics

### 13.1 Input inventory

Required outputs:

- files supplied,
- formats,
- row counts,
- version IDs,
- file hashes,
- optional fields present,
- mapping applied.

Evidence class:

```text
observed_fact
```

### 13.2 Exact duplicates

Required output:

- exact duplicate count under documented normalization,
- duplicate groups by ID,
- optional redacted examples.

Evidence class:

```text
observed_fact
```

### 13.3 Support size

Required output:

- distinct state count under the declared representation.

Evidence class:

```text
derived_metric
```

### 13.4 Gini-Simpson diversity

Required default diversity metric:

\[
D=1-\sum_i p_i^2
\]

Evidence class:

```text
derived_metric
```

Required report metadata:

- representation,
- number of states,
- weighting mode,
- missing-state handling.

### 13.5 Tail membership

Tail membership uses a declared threshold rule.

Recommended hero default:

```text
tail_rule: singleton_count
tail_count_threshold: 1
```

Evidence class:

```text
derived_metric
```

### 13.6 Rare-state ranking

States are ranked by observed frequency and approved tie-breaking rules.

Evidence class:

```text
derived_metric
```

### 13.7 One-step extinction scenario

For state frequency \(p_i\) and sample size \(n\):

\[
P_{\text{absent,next}}=(1-p_i)^n
\]

Evidence class:

```text
simulation
```

Required assumptions:

- categorical states,
- multinomial sampling,
- one-step horizon,
- closed process unless reopening is included,
- declared sample size,
- declared representation.

### 13.8 Tail fragility warning

A warning may summarize rare-state vulnerability under the approved scenario.

Evidence class:

```text
proxy_signal
```

The warning must not present the scenario as a calibrated real-pipeline forecast.

## 14. Provenance diagnostics

### 14.1 Provenance row coverage

\[
\text{row coverage}
=
\frac{\text{records with matching provenance rows}}
{\text{total records}}
\]

Evidence class:

```text
observed_fact
```

### 14.2 Required-field coverage

Measures records whose required provenance fields are present and valid.

Evidence class:

```text
observed_fact
```

### 14.3 Grounding-field coverage

Measures records whose `external_grounding` value is `yes` or `no`.

Evidence class:

```text
observed_fact
```

### 14.4 Source-type shares

Default source categories:

- human,
- synthetic,
- mixed,
- sensor,
- unknown.

Default shares are unweighted.

Evidence class:

```text
derived_metric
```

### 14.5 Direct closure exposure bounds

Recommended operationalization, pending `UD-010` approval:

\[
C_{\min}
=
\frac{N_{\text{known closed}}}{N_{\text{total}}}
\]

\[
C_{\max}
=
\frac{N_{\text{known closed}}+N_{\text{unresolved}}}{N_{\text{total}}}
\]

Evidence class:

```text
derived_metric
```

Required label:

```text
toolkit_operationalization
```

The report must disclose that the bound depends on declared grounding evidence.

### 14.6 Grounding authority

Direct grounding claims use `external_grounding`.

The toolkit must not infer grounding from:

- source type,
- human review,
- content style,
- generator ID,
- source reputation,
- filename.

## 15. Lineage diagnostics

### 15.1 Graph model

The lineage graph connects records through declared parent references.

Canonical node identity:

```text
(dataset_version, record_id)
```

### 15.2 Cycle status

Cycle detection is a graph-validity rule for generational ancestry.

A cycle blocks ancestry interpretation for the affected graph.

Evidence class:

```text
observed_fact
```

or:

```text
error
```

### 15.3 Lineage coverage

Required outputs:

- records with parent fields,
- resolvable parent edges,
- unresolved parent edges,
- ambiguous edges,
- records with resolved external ancestry.

Evidence class:

```text
observed_fact
```

and:

```text
derived_metric
```

for shares.

### 15.4 External roots

An external root anchors an externally grounded ancestry path under the approved definition.

Required outputs:

- distinct external-root count,
- root IDs,
- records supported by each root,
- unresolved ancestry count.

Evidence class:

```text
derived_metric
```

### 15.5 Ancestor incidence

For each ancestor, report the number and share of analyzed records with that ancestor in their reachable root set.

Evidence class:

```text
derived_metric
```

### 15.6 Ancestry concentration

Recommended optional concentration method:

For a record with \(k\) reachable external roots, allocate \(1/k\) mass to each root.

After aggregation, let normalized root shares be \(w_a\).

\[
HHI_{\text{ancestry}}=\sum_a w_a^2
\]

\[
N_{\text{effective roots}}=\frac{1}{HHI_{\text{ancestry}}}
\]

Evidence class:

```text
derived_metric
```

Required limitation:

The metric describes topology. It does not establish causal contribution or semantic error.

### 15.7 Correlated-error exposure

A shared-ancestry warning may identify dependence concentration.

Evidence class:

```text
proxy_signal
```

Required limitation:

Shared ancestry does not prove shared downstream error.

## 16. Longitudinal diagnostics

### 16.1 Ordering requirement

Version comparison requires an explicit ordering rule from:

- configuration,
- timestamps,
- user-declared CLI order.

Filename or lexical ordering alone is insufficient.

### 16.2 Required compatible representation

Support and tail comparisons require the same or explicitly mapped representation.

### 16.3 Version delta outputs

Required Level 4 outputs:

- record-count delta,
- support delta,
- diversity delta,
- added states,
- missing states,
- provenance-coverage delta,
- source-share delta.

### 16.4 Tail extinction

A state present in an earlier version and absent from a later compatible version may be reported as extinct under that representation.

Evidence class:

```text
derived_metric
```

Required wording:

```text
extinct from the observed later version under the declared representation
```

Do not claim permanent extinction from the full production process.

### 16.5 Lineage change

When compatible lineage exists across versions, optional outputs may include:

- external-root count change,
- ancestry concentration change,
- unresolved-parent change,
- grounding coverage change.

### 16.6 Model longitudinal capability

Model-performance or behavior trends remain unavailable unless separate approved model evidence is supplied.

up to approximately 100,000 records

## 25. Product acceptance criteria

v0.1 is complete only when all required conditions pass.

### 25.1 New-user usability

A new user can:

1. install the package,
2. run the hero example in one command,
3. find the generated reports,
4. understand the observability level,
5. identify unavailable conclusions.

### 25.2 Auditability

Every public result traces to:

- definition,
- Theory Map ID or product basis,
- module,
- test,
- report field,
- limit.

### 25.3 Honest limits

The hero report must state that:

- model-performance decline is unavailable,
- universal collapse is unavailable,
- ancestry concentration is not causal proof.

### 25.4 Low-observability value

Level 1 and Level 2 runs must still produce useful output.

Examples:

- exact duplicates,
- support,
- diversity,
- provenance gaps,
- closure bounds.

### 25.5 Lineage value

Level 3 must identify:

- cycles,
- external roots,
- shared ancestors,
- ancestry concentration,
- unresolved ancestry.

### 25.6 Longitudinal value

Level 4 must identify:

- support changes,
- missing states,
- tail extinction,
- source-share changes.

### 25.7 Reproducibility

Same inputs, configuration, version, and seed produce the same public output.

### 25.8 Failure clarity

Invalid inputs produce:

- exact error code,
- clear cause,
- affected field or record,
- no raw-content leakage.

### 25.9 Privacy

The hero example runs:

- without network access,
- without telemetry,
- without raw content in normal logs.

### 25.10 Performance

The hero example meets the runtime target.

## 28. Product language rules

### 28.1 Preferred terms

Use:

- recursive closure exposure,
- support contraction,
- diversity contraction,
- tail vulnerability,
- tail extinction,
- provenance incompleteness,
- grounding coverage,
- external ancestry,
- ancestry concentration,
- simulation,

### 28.2 Restricted term

`collapse` may appear in:

- project motivation,
- theory references,
- cited research names,
- unavailable conclusions.

It must not appear as:

- a metric,
- a score,
- a direct alert,
- a universal prediction.

### 28.3 Causal restraint

Do not state that:

- entropy caused a result,
- a shared ancestor caused an error,
- synthetic origin caused failure,
- human origin established grounding,
- low diversity proved failure.
